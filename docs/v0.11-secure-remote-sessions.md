# v0.11 — Secure remote sessions

## Product goal

A Grok UI user can start work on one trusted computer, leave that computer, and
continue the same Grok conversation from a phone or another computer over their
private Tailscale network or an SSH tunnel.

This is a live session experience, not a remote terminal. The user sees Grok's
messages, reasoning summaries, tool activity, status, and permission requests.
They can send a follow-up, choose one of Grok's real permission options, or
interrupt the current turn.

## The first user journey

1. Joey runs the Grok UI host agent on his desktop with monitoring and remote
   sessions configured with two different long random tokens.
2. He registers that host in Fleet, explicitly enables remote sessions, and
   enters the matching control token.
3. While the host is healthy and fresh, he starts a session in a workspace the
   host has already observed, or opens an existing managed remote session.
4. The Remote Session Console streams the same structured conversation and tool
   activity he would see locally.
5. If Grok asks for permission, Joey chooses only from the options Grok sent.
6. If the network drops, the console reconnects and reconciles with host-owned
   state. It does not claim that an unconfirmed command succeeded.

## MVP actions

| User action | Meaning | Failure behavior |
| --- | --- | --- |
| Start | Create one ACP-managed Grok session in a previously observed workspace and send its first prompt. | Disabled unless the host is healthy, fresh, enabled, and capable. A retry reuses the same command ID. |
| Follow up | Send another natural-language message into the same session, like continuing in the Grok CLI. | A delivery with an unknown outcome is reconciled; it is never silently sent twice. |
| Allow or deny | Resolve a pending request using an exact option advertised by Grok. | A stale or invented option is rejected by the host. |
| Interrupt | Ask Grok to cancel the active turn while leaving the session available for another follow-up. | The console shows reconciliation if the connection drops before the result is known. |

Pause, Resume, and Stop are deliberately not overloaded onto this session MVP.
Interrupt already provides the immediate safety action for a running turn.
Workflow lifecycle controls can follow once Grok exposes stable remote handles
and the product defines the destructive confirmation boundary.

## Connection and observable state

The host remains the source of truth. A remote session snapshot contains a
bounded transcript, controller state, pending permissions, and a revision.
The central server opens a dedicated server-sent event stream and polls the host
through the constrained control connector. Only changed revisions are emitted,
with periodic heartbeats.

When connectivity is lost:

- the transcript already displayed remains visible as historical context;
- the console visibly reports reconnecting or unavailable;
- follow-up, permission, and interrupt controls are disabled once the central
  monitor no longer considers the host healthy and fresh;
- the central server enforces the same gate even if an older browser has not
  updated yet;
- reconnect reloads the complete bounded host snapshot rather than guessing
  which local UI state is current.

## Authorization model

v0.11 stays deliberately smaller than enterprise IAM:

- Monitoring uses `GROK_UI_AGENT_TOKEN` and remains GET/HEAD-only.
- Remote sessions use a distinct `GROK_UI_AGENT_CONTROL_TOKEN`.
- The host agent exposes no control routes unless that second token is present.
- The central Fleet entry also requires an explicit Remote Sessions toggle and
  the matching control token.
- Each host grants or denies control independently.
- The browser never receives either host credential.
- The host advertises individual capabilities for session read, create,
  follow-up, interrupt, and permission resolution.

Team roles and shared access are deferred. A later small-team model can start
with Owner and Operator roles, host-by-host grants, and optional second-person
approval for destructive workflow actions. It should not add directory sync,
policy languages, or organization hierarchies to the local-first MVP.

## Command delivery and reconciliation

Every mutation carries a client-generated command ID and expiry. The host:

1. validates an expiry no more than 15 minutes in the future;
2. hashes the canonical payload without retaining the prompt;
3. durably records acceptance before running the command;
4. returns the stored outcome when the same ID, action, target, actor, expiry,
   and payload are retried;
5. rejects reuse of the ID for a different command;
6. coalesces concurrent retries while an operation is in flight;
7. marks an accepted or executing command `unknown` after host restart and
   never replays it automatically.

This gives the UI three honest outcomes:

- `completed`: the host confirmed the command;
- `failed`: the host confirmed failure and the UI may offer a deliberate retry;
- `unknown`: execution may have happened, so the UI reconciles session state
  instead of creating a duplicate.

The client uses a 10-minute delivery window. An expired command is rejected
even after its detailed record has been compacted, so bounded retention cannot
turn an old retry into new work. The host retains at most 1,000 unexpired
command records and applies backpressure instead of evicting active replay
protection.

The private `remote-commands.json` file also stores at most 1,000 audit
transitions using user-only directory and file permissions. Audit rows contain
the command ID, action kind, target, token fingerprint, timestamp, and outcome.
Prompts, provider error details, secrets, and transcript content are not audit
fields.

## Trust and safety boundaries

- There is no arbitrary shell, arbitrary URL fetch, file mutation API, or raw
  command input.
- Remote Start accepts only a workspace already observed by the host.
- A control token cannot be the monitoring token.
- Credentials stay server-side and are stripped from browser/API projections.
- The central connector permits only documented `/agent/control/v1/` routes,
  rejects redirects, caps request and response bodies, and applies a timeout.
- A host may omit or revoke any capability and remains the local control
  authority.
- Existing CLI-observed sessions stay read-only. The control plane continues
  only sessions created or restored as host-managed sessions.
- Permission resolution accepts only the session, request, and option currently
  advertised by Grok.
- Stale, unhealthy, incompatible, disabled, or incapable hosts cannot receive a
  mutation.
- Interruption and future destructive actions remain explicit and reviewable.

## Acceptance matrix

| Requirement | Evidence |
| --- | --- |
| Monitoring remains read-only | The existing `/agent/v1/` middleware still permits only GET/HEAD; its token cannot call control routes. |
| Control is explicit per host | Separate host environment variable, separate registry secret, registry opt-in, and negotiated capability checks. |
| Live conversation continues remotely | Remote Session Console renders structured session events and sends natural-language follow-ups. |
| Permissions cannot be fabricated | Host validates the pending request and exact advertised option. |
| Disconnects do not duplicate work | Durable command IDs, payload fingerprints, in-flight joining, unknown-after-restart behavior, and full snapshot reconciliation. |
| Secrets and prompts are not audit data | Public-config parser rejection plus fingerprint-only bounded command/audit storage. |
| Stale clients cannot act blindly | UI disables controls and the central monitor independently gates every mutation on live host state. |
| End-to-end behavior is covered | Browser fixture exercises Start, live reply, permission resolution, follow-up, and Interrupt through the production UI. |

## Later additions and open decisions

The next design discussion should decide:

1. Whether remote workflow Pause and Resume are reversible enough to be
   immediate, while Stop requires a confirmation describing the affected run.
2. Whether destructive Stop needs typed confirmation for solo use and a second
   person for shared/team hosts.
3. Whether remote session expiry should be based on inactivity, host policy, or
   an explicit detach action.
4. Whether users need an in-product audit viewer or whether the private host
   record is sufficient for the first release.
5. Whether an existing CLI-started session can be safely attached for control,
   or whether v0.11 should control only sessions created through the host agent.

The recommended default is to ship the current managed-session-only MVP, gather
reconnection and permission evidence, then add workflow controls and small-team
roles as separate reviewed slices.
