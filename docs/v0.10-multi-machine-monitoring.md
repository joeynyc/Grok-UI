# v0.10 Multi-machine Monitoring implementation plan

This milestone extends the local session, workflow, runtime, usage, privacy,
authentication, reconnect, and persistence architecture shipped in v0.9. It
does not introduce a second local tracker, a remote control plane, shell
execution, arbitrary endpoint probing, or destructive controls.

## Architecture audit

### Foundations retained from v0.9

- `GrokStore`, `LiveMonitor`, `GrokController`, `RuntimeInspector`, and
  `UsageLedger` remain the canonical local projections. The host agent exports
  bounded read-only views of those projections rather than rebuilding them.
- `SessionStateStore` remains unchanged as the atomic, user-private state
  boundary for existing UI-owned data. Fleet configuration is isolated in its
  own atomic `fleet.json` registry so adding hosts cannot rewrite annotations,
  managed sessions, usage, budgets, or alerts.
- `SecurityGate` remains the browser-facing authentication boundary. Host-agent
  authentication is separate so a fleet credential cannot become a browser
  session or an ACP control credential.
- Privacy Mode remains a persistent presentation safeguard. It applies the
  existing stable aliases to remote host and workload values without changing
  the underlying authorized API contract.
- Local SSE, ACP recovery, interruption semantics, and local-first startup
  remain available even when every configured remote host is unavailable.

### v0.10 trust boundaries

1. A lightweight agent runs beside an existing Grok UI installation and
   publishes only the documented monitoring protocol.
2. The central Grok UI server polls only explicitly registered agent endpoints.
   Polling uses bounded time, concurrency, response size, and record counts.
3. SSH port forwarding and a private Tailscale network are supported deployment
   topologies. The SSH transport may spawn the system `ssh` executable with a
   fixed argument array and no shell. Grok UI does not run arbitrary SSH
   commands, invoke `tailscale`, or perform discovery commands.
4. Remote credentials are server-side only. They are not returned through the
   browser fleet contract, included in errors, or written to logs.
5. Remote sessions, workflows, runtime state, and usage are read-only in v0.10.
   Remote start, prompt, approve, pause, resume, interrupt, stop, shell, diff,
   arbitrary fetch, and destructive endpoints are intentionally absent.

## Protocol and status model

The wire protocol is version `1`; both the central monitor and host agent
currently advertise a supported range of `1` through `1`. Compatibility is an
overlap check, so an agent is incompatible when its advertised range does not
include a version the central monitor supports.

| Boundary | Implemented limit |
| --- | ---: |
| Registered hosts | 32 |
| Agent response body | 2 MiB |
| Central fleet snapshot | 4 MiB |
| Agent request timeout | 3.5 seconds |
| Fleet poll interval | 5 seconds |
| High-latency threshold | greater than 1.5 seconds |
| Stale threshold | 15 seconds since the last success |
| Offline threshold | 45 seconds since the last success |
| Concurrent remote reads | 4 globally, including polling and user-requested reads |
| Failure backoff | 5, 10, 20, then at most 30 seconds |
| Capabilities per host | 16 |
| Sessions per snapshot | 200 |
| Workflows per snapshot | 100 |
| Transcript items per session detail | 200 |
| Usage ledger entries per snapshot | 1,000 |

The connector accepts only fixed paths beneath `/agent/v1/`, sends authenticated
`GET` requests, refuses redirects, checks both declared and streamed response
size, and parses JSON only after the complete bounded body is received.
The central monitor also compacts oversized per-host projections to keep its
browser and SSE fleet snapshot at or below 4 MiB. Unchanged fleets are not
re-emitted every second; status and freshness threshold changes still emit.

| Agent route | Read-only result |
| --- | --- |
| `GET /agent/v1/hello` | Protocol range, stable host identity, versions, and capabilities |
| `GET /agent/v1/snapshot` | Health plus bounded sessions, workflows, runtime, and default usage |
| `GET /agent/v1/sessions/:id` | One bounded session detail and transcript |
| `GET /agent/v1/usage` | Bounded usage report for validated period, scope, and grouping |

Every agent route requires `Authorization: Bearer <dedicated-agent-token>`.
`HEAD` is allowed by the read-only boundary; other methods receive `405` with
`Allow: GET, HEAD`. Unknown protocol routes receive `404`, and collection
failures return a generic `503`.

The browser-facing central API remains behind the existing `SecurityGate`.
Registry mutations change only central connection settings; they do not mutate
the remote host:

| Central route | Result |
| --- | --- |
| `GET /api/fleet` | Current registry, health, and bounded snapshots |
| `POST /api/fleet/hosts` | Add one central registry entry |
| `PATCH /api/fleet/hosts/:id` | Update one central registry entry |
| `DELETE /api/fleet/hosts/:id` | Remove one central registry entry |
| `POST /api/fleet/hosts/:id/refresh` | Request an immediate read-only poll |
| `GET /api/fleet/hosts/:id/sessions/:sessionId` | Fetch one namespaced remote session detail |
| `GET /api/fleet/hosts/:id/usage` | Fetch one validated remote usage report |

Registry URLs are origins, not arbitrary request URLs. Direct transport accepts
only HTTP or HTTPS loopback origins. Tailscale transport accepts HTTP or HTTPS
origins addressed by a `.ts.net` name, a `100.64.0.0/10` IPv4 address, or a
Tailscale `fd7a:115c:a1e0::/48` IPv6 address. User information, paths, query
strings, and fragments are rejected.

SSH transport requires a validated `user@host` or host target, an SSH port, a
fixed loopback local port, and an agent port that defaults to `4311`. It starts:

```text
ssh -N -T -o BatchMode=yes -o ConnectTimeout=<bounded-seconds>
  -o ExitOnForwardFailure=yes -o ServerAliveInterval=10
  -o ServerAliveCountMax=2 -p <ssh-port>
  -L 127.0.0.1:<local-port>:127.0.0.1:<agent-port> -- <target>
```

Arguments are passed directly with no shell and no remote command.
Enabled SSH registry entries must use distinct local ports. Before a new tunnel
starts, the connector rejects a loopback port that is already accepting
connections. After spawning `ssh`, it waits for that exact listener to become
ready and keeps the whole operation inside the original request deadline.

The host agent defaults to `127.0.0.1:4311`. It requires
`GROK_UI_AGENT_TOKEN`; `GROK_UI_AGENT_HOST`, `GROK_UI_AGENT_PORT`, and
`GROK_UI_AGENT_LABEL` configure its bind and presentation identity. Its stable
identity is created atomically in the private state directory as `host.json`.

The separate `fleet.json` registry uses schema version 1. The state directory
and file use `0700` and `0600` permissions. A malformed registry, invalid
persisted host, or future schema version is preserved rather than overwritten;
the central UI loads with an empty fleet plus `registryError`, and registry
mutations remain blocked until the file is repaired.

Registry mutations are transactional: they validate and persist a candidate
map before exposing it in memory. Failed writes leave both memory and disk on
the previous version, do not poison later writes, and preserve atomic
temporary-file replacement.

The polling interval and freshness thresholds are reported in every central
fleet snapshot. Freshness is `fresh` for less than 10 seconds since success,
`aging` from 10 to less than 15 seconds, `stale` from 15 to less than 45
seconds, and `expired` at 45 seconds.

| Host status | Meaning |
| --- | --- |
| `connecting` | Enabled and waiting for the first successful sample, including the first two reachability failures |
| `healthy` | A complete compatible snapshot arrived within the latency threshold |
| `degraded` | The agent reports degraded health, any section is partial or unavailable, a cap truncated data, latency exceeds 1.5 seconds, or a previously healthy host has a recent failure |
| `stale` | The last success is at least 15 seconds old but less than 45 seconds old |
| `offline` | No first sample succeeded after three failures, or the last success is at least 45 seconds old |
| `incompatible` | The hello protocol range does not overlap version 1, or the snapshot envelope is not version 1 |
| `unauthorized` | The agent returns `401` or `403` for its dedicated token |
| `unavailable` | Monitoring is disabled, or a malformed first response cannot produce a usable snapshot |

## Delivery plan

### Increment 1 — Host-agent protocol

- Export stable host identity, Grok UI and agent versions, negotiated
  capabilities, health, and bounded snapshots through authenticated read-only
  routes.
- Reuse the existing local projections and their provenance semantics.
- Reject malformed authentication and unsupported methods without exposing
  local credentials or control routes.

### Increment 2 — Registry, connectivity, and health

- Persist a bounded central host registry atomically in a separate private
  `fleet.json` file without changing the existing v3 session state.
- Poll explicitly configured SSH-forwarded or Tailscale-oriented endpoints with
  bounded timeouts, safe parsing, and per-host failure isolation. SSH forwarding
  uses a fixed, argument-separated process invocation and never a shell.
- Project connecting, healthy, degraded, stale, offline, incompatible,
  unauthorized, and unavailable behavior without treating an old snapshot as
  current.

### Increment 3 — Read-only fleet experience

- Add a fleet health view with host identity, versions, capabilities, latency,
  last seen, freshness, and status.
- Namespace remote workloads by host so equal session or workflow identifiers
  cannot collide.
- Expose remote sessions, workflows, runtime state, and usage without rendering
  any remote mutation affordance.
- Apply Privacy Mode aliases to remote names, identifiers, paths, content, and
  runtime metadata.

### Increment 4 — Hardening and release candidate

- Cover parsers, registry recovery, compatibility, authentication, caps, state
  transitions, and aggregation with unit and integration tests.
- Exercise multiple mock hosts, disconnect and reconnect, all explicit failure
  states, Privacy Mode, responsive layout, and the absence of controls in a
  production browser journey.
- Run a 75-second multi-host soak, packed-install interoperability smoke,
  privacy and security checks, and `npm audit`.

### Post-review architecture hardening

Independent Grok and Claude reviews of the first candidate identified several
cross-layer risks. The remediation keeps the same product scope while making
the boundaries explicit:

- the central server and host agent share session-row projection code, while
  the agent composes current usage observations without becoming another
  durable-state writer
- refresh coalesces with active polling, unchanged snapshots do not force SSE
  frames, aggregate compaction uses per-host size deltas, and connection
  generations prevent old in-flight requests from overwriting new settings
- registry transactions recover from failed writes and reject conflicting SSH
  forwarding ports
- the connector validates fixed paths before any fetch, waits for SSH
  forwarding readiness, rejects redirects, and bounds streamed bodies
- the browser validates and caps remote session detail before rendering it
- Privacy Mode covers session-detail model labels and registry errors, while
  status narratives retain safe generic operational meaning
- cached observations remain available for context but are explicitly marked
  historical during reconnect, disablement, incompatibility, and failures;
  preserved registry-load errors are visible in the Fleet page
- `FleetView.tsx` owns page coordination only; selectors, status, the registry
  editor, five telemetry panels, and Fleet CSS have separate owners under
  `src/views/fleet/` and `src/styles/fleet.css`
